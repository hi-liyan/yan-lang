# Yan 语言设计基线

日期：2026-08-18  
状态：方向设计，尚未进入实现  
替代：此前所有以 Web 后端资源模型为中心的 Yan 设计

## 1. 定位

Yan 是一门面向个人开发者使用 AI 快速开发、快速交付的轻量编译型通用编程语言。

Yan 的目标是让个人开发者以有限的运维成本交付 Web 服务、CLI、自动化工具、桌面辅助工具和后台任务，同时保持项目在多轮 AI 修改后仍然可理解、可验证、可维护。

Yan 不是 Rust 的简写，也不是 Web DSL。它应具备独立的语言规范、类型系统、标准库、包格式、诊断和工具链。HTTP、数据库、GUI 或 AI 调用均是库能力，而非语言关键字。

### 1.1 核心口号

> 一门面向个人开发者使用 AI 可以快速开发、快速交付的轻量编译型编程语言。

### 1.2 设计优先级

1. 低认知负担：少概念、少语法分支、少隐式规则。
2. AI 可维护性：项目的正确结构可被工具检查，不依赖长篇提示词约束。
3. 可交付性：产物是轻量、可复制部署的原生可执行程序。
4. 生态复用：优先接入现有成熟生态，不重造 async、HTTP、TLS、数据库驱动等基础设施。
5. 长期独立性：后端实现策略不成为语言语义；Yan 程序不应被 Rust 源码泄漏所定义。

### 1.3 非目标

v0.1 不试图：

- 替代 C 或 Rust 做系统级编程。
- 提供零成本手工内存控制或暴露借用检查。
- 成为动态脚本语言或运行时反射平台。
- 通过宏、继承层级、复杂泛型或隐式魔法提高抽象能力。
- 自研 HTTP server、数据库驱动、异步调度器、TLS 或包仓库协议。

## 2. Yan 的价值

Rust 已能提供优秀性能和部署体积，但其所有权、生命周期、trait、泛型边界和生态选择对个人开发者及 AI 都有较高成本。AI 可以生成 Rust，却常在多轮修改后引入不必要的抽象、生命周期冲突、过度 clone、trait 泛化和不一致的错误边界。

Yan 的价值不在于生成比 Rust 更快的程序，而在于提供比 Rust 小得多的应用开发状态空间：

- 一个功能有少量规范写法，而非任意框架与模式组合。
- 所有公开边界都有明确类型、错误和依赖。
- 架构违规由编译器拒绝，而非由 code review 猜测。
- 格式、目录、包和依赖图稳定，使 AI 能读取和修改一个可验证的项目模型。

因此，Yan 应把开发者从 Rust 的底层表达能力中解放出来，同时继续把 Rust 作为第一阶段的工程基础设施。

## 3. 语言与实现后端

Yan 的用户模型是“Yan 编译为可执行程序”，不是“用户维护 Rust 项目”。

第一阶段采用 Rust 作为后端：

```text
Yan 源码 -> Yan 前端与架构检查 -> 生成 Rust 构建产物 -> Cargo/rustc -> 原生可执行文件
```

生成的 Rust 只属于构建目录，不是公开 API，也不允许手工修改。Yan 的类型、错误、包、标准库和编译诊断必须由 Yan 自己定义。

这条路线复用 Rust 的优化器、跨平台链接、Cargo 依赖解析、Tokio、HTTP 和数据库生态，显著降低早期实现风险。未来可按需要替换或增加直接原生后端；这不应改变 Yan 源程序的语义。

### 3.1 为什么不直接使用 Rust

直接使用 Rust 更适合需要精确资源控制、复杂并发模型或深度访问 Rust crate 的场景。Yan 服务于另一类优化目标：个人开发者与 AI 以稳定范式快速交付应用。

Yan 通过受限的语言面和项目约束，消除 Rust 应用开发中最常见的决策负担：运行时组合、Web 框架选择、错误库选择、序列化方式、依赖层级和大量 trait 驱动的抽象。性能与部署能力来自 Rust 后端，应用开发体验和可维护性来自 Yan。

## 4. 最小通用语言内核

语言内核不包含任何 Web 或数据库概念。

### 4.1 值与类型

v0.1 支持：

- `bool`、`int`、`float`、`string`、`bytes`、`unit`。
- `list<T>`、`map<string, T>`、`option<T>`、`result<T, E>`。
- 具名字段 `struct` 与封闭 `enum`。
- 用户定义的 `type` 新类型，不提供隐式转换。

`int` 固定为有符号 64 位整数，`float` 固定为 IEEE 754 `f64`，`string` 固定为 UTF-8。没有 `null`，没有 `any`，没有隐式数值转换。

### 4.2 控制流与函数

支持 `fn`、`let`、`mut`、`if`、`match`、`for`、`while`、`return` 和 `?`。函数、参数和返回类型均显式声明；只有 `if`、`match` 和代码块可作为表达式产生值。

`?` 仅可传播相同错误类型的 `result<T, E>`。错误域转换必须显式调用 `map_err` 或使用 `match`，避免 AI 在隐式转换中丢失业务语义。

### 4.3 有意缺失的能力

v0.1 不支持类、继承、反射、宏、用户自定义运算符、异常、全局可变状态、函数重载、隐式转换、协变容器、复杂泛型和用户定义 trait。

这些限制不是表达能力缺陷，而是控制项目状态空间的机制。需要复用逻辑时使用普通函数、组合和封闭数据类型。

### 4.4 模块与文件

一个 `.yan` 文件对应一个 module。目录只负责组织模块命名空间，不构成独立 module；Yan 不使用 `mod.yan`、`mod.rs`、内联模块或额外文件加载声明。

源文件可在文件头显式声明模块：

```yan
module tasks.service
```

也可省略该声明。省略时，编译器从项目 `src/` 下的文件路径推导模块名；例如 `src/tasks/service.yan` 对应 `tasks.service`。显式声明存在时必须与路径推导结果完全一致，否则为编译错误。

`package` 保留给未来 `yan.project` 中可发布、可依赖和带版本的交付单元，不作为源文件命名空间关键字。

## 5. 可维护性即语言能力

Yan 的核心差异化在于可强制执行的项目契约。

### 5.1 固定工具链

- 一个官方 formatter，格式不可配置。
- 一个官方包清单和锁文件。
- 一个官方测试命令和诊断格式。
- 规范的目录与模块映射，不允许隐式加载文件。
- 公共 API 自动导出为机器可读清单。

### 5.2 依赖方向

每个包必须声明层级及可依赖的包。默认分层为：

```text
interface -> application -> domain -> foundation
infrastructure -> application / foundation
```

其中 `domain` 不可导入 `interface` 或 `infrastructure`。HTTP、数据库、文件系统和第三方 SDK 只能由 `interface` 或 `infrastructure` 包访问。编译器必须在依赖违规时失败。

这不是强制 DDD；它是避免 AI 将请求处理、持久化、鉴权和业务规则堆入同一文件的最小结构约束。

### 5.3 显式边界

- 所有公共函数必须声明参数、返回类型与错误类型。
- 跨包数据必须是 `struct`、`enum` 或显式 `type`，不允许无类型 JSON 值。
- JSON、环境变量、命令行和数据库行都必须在边界转换为显式类型。
- 副作用只能来自标准库声明的 capability，例如 `http`、`db`、`fs`、`clock`。
- 核心业务包不可直接获得 capability。

### 5.4 AI 工具契约

编译器应提供稳定 JSON 输出：模块图、公共 API、依赖图、capability 使用图、诊断与变更影响范围。AI IDE 或 CLI 在修改前读取这些产物，在修改后运行格式、类型、架构和测试检查。

语言不应以“AI 自动生成”替代工程判断；它要让 AI 的每次输出有可验证的结构、边界和反馈。

## 6. 副作用与并发

Yan 不承诺 Rust 式内存安全，也不暴露 Rust 式借用模型。v0.1 的安全边界是：不可变业务值、无全局可变状态、受 capability 约束的 I/O，以及受限的并发模型。

### 6.1 Capability

副作用 API 必须显式接收 capability。例如数据库函数接收 `db: Db`，文件操作接收 `fs: Fs`。capability 只能在应用组合根创建并向外层传递，不可由 domain 包构造。

这同时实现最小权限、可替换测试实现和可静态审计的副作用边界。

### 6.2 并发

v0.1 仅支持 `async fn` 与 `await`，不直接暴露线程、锁、共享内存或裸任务。并发工作由标准库提供结构化 API：任务必须被等待、取消或返回受控句柄；不允许静默后台任务。

共享可变状态必须通过标准库的 actor 或持久化接口表达。该选择牺牲一部分底层灵活性，换取更易被 AI 保持正确的并发模型。

## 7. 标准库与生态

Yan 标准库分为两层：

- `yan.core`：集合、文本、时间、错误、编码、测试与并发基础。
- `yan.platform`：HTTP、JSON、数据库、文件、CLI、日志、配置、进程与 AI Provider API。

`yan.platform` 的实现优先包装稳定 Rust crate，并保持 Yan 侧 API 独立稳定。个人项目只需使用官方选定组合，而不是每次从数个 Rust 框架中挑选。

第三方生态接入采用 adapter 包：由 Rust crate 实现，向 Yan 暴露受限、文档化、类型稳定的 API。v0.1 禁止 Yan 直接调用任意 Rust API，防止 Rust 类型系统和生命周期细节泄漏进 Yan。

Rust adapter 的边界约束与未决问题见 [Rust 生态互操作探讨](discussions/rust-interoperability.md)。

## 8. Web 是第一个平台，而不是语言本体

第一个官方应用模板可以是 Web API：路由、JSON、认证中间件、Postgres、迁移、日志与 Docker 构建。但这些都是 `yan.platform.http` 和 `yan.platform.db` 包能力，不是 `route`、`endpoint` 等语言关键字。

因此同一门语言还能自然用于：

- CLI 与开发者工具。
- 定时任务与自动化。
- 数据同步、爬取和文件处理。
- AI Agent 的工具服务与工作流编排。
- 未来的桌面或 WASI 应用。

## 9. v0.1 可交付边界

v0.1 的成功标准是，一个个人开发者可以稳定地实现并部署一个小型应用，而不是证明 Yan 能覆盖所有语言领域。

必须交付：

- 编译器 CLI、parser、类型检查、模块解析和规范 formatter。
- 原生可执行文件构建和 Docker 交付模板。
- `yan project` 包清单、锁文件和依赖方向检查。
- core 标准库与 HTTP/JSON/CLI/文件系统能力。
- 结构化 async 与测试框架。
- Rust adapter ABI，以及一个 HTTP + Postgres 官方示例。

明确延后：直接机器码后端、插件市场、GUI、泛型函数、用户 trait、FFI 直连、分布式 actor、ORM、反射和宏。

## 10. 实施顺序

1. 固定语法、类型、模块、错误和 capability 的最小规范，并为每条规则编写正反例。
2. 建立 Rust workspace，实现 lexer、parser、AST、诊断和 formatter。
3. 实现模块解析、类型检查、依赖方向检查与项目清单。
4. 生成最小 Rust 程序，先支持 CLI 与纯函数测试。
5. 增加受控的 HTTP/JSON 平台库，再增加数据库 adapter。
6. 仅在端到端交付体验稳定后，评估 async、更多平台库和独立后端。

## 11. 决策原则

新增一个特性前必须回答：它是否减少个人开发者或 AI 的长期决策数量？它是否有唯一或极少数惯用写法？它是否可由编译器、formatter 或架构检查器验证？它是否应当只是标准库能力？

若答案不能清晰成立，默认不加入语言核心。
