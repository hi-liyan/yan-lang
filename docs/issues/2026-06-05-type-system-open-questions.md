# Yan 类型系统待定课题

日期：2026-06-05  
状态：待讨论

## 1. 目的

本文档用于集中整理 Yan 当前类型系统设计中已经暴露出来、但尚未定稿的问题。

这些问题虽然来自示例代码中的局部疑问，例如 `UserId`、`Email`、`Json<T>`、`Result<T, E>` 的使用方式，但本质上会影响：

- Yan 的基础类型系统
- 业务建模能力
- 语法层的一致性
- 编译器的类型检查边界
- 标准库的职责划分

因此，需要将这些问题从零散讨论中抽离出来，作为独立课题推进。

## 2. 课题范围

当前需要集中讨论的核心问题包括：

- `UserId` 这类名称到底是不是类型
- 业务标识类型应如何声明
- 类型别名与新类型应如何区分
- `Email`、`Url` 这类受约束类型应如何表达
- `check ... else ...` 这类校验语法与类型系统如何配合
- `Json<T>` 这类包装类型是否属于语言推荐模型
- `Result<T, E>`、`Option<T>` 是否作为核心内建泛型

## 3. 课题一：`UserId` 是否为真正的类型

### 3.1 背景

当前示例中存在如下写法：

```yan
record UserView {
  id: UserId
  name: Str
  email: Str
}
```

这里会引出一个直接问题：`UserId` 是不是一个真正的类型？

### 3.2 为什么这是个问题

如果 `UserId` 只是 `Int` 的普通别名，那么：

- 文档可读性更好
- 但类型系统未必真正区分 `UserId` 和 `Int`

这样就无法完全防止把不同业务标识混用。

例如：

```yan
fn load_user(user_id: UserId, order_id: OrderId) -> Result<User, UserError> {
  ...
}
```

如果 `UserId` 和 `OrderId` 最终都退化成 `Int`，那么很多本应由类型系统阻止的错误依然可能发生。

### 3.3 待定问题

需要明确：

- `UserId` 是否必须是独立类型
- 业务标识类型是否允许零成本封装基础类型
- 标识类型之间是否必须强隔离

### 3.4 当前倾向

当前更倾向：`UserId` 应是独立类型，而不是简单别名。

## 4. 课题二：类型别名与新类型如何区分

### 4.1 问题描述

Yan 需要明确区分以下两种需求：

1. 只是为了可读性重命名类型
2. 需要一个真正独立的新类型

例如：

```yan
type UserName = Str
```

与：

```yan
newtype UserId = Int
```

语义上并不相同。

### 4.2 需要决定的内容

- Yan 是否同时支持“类型别名”和“新类型”
- 这两者的语法如何区分
- 是否需要引入新的关键字，例如 `type`、`newtype`
- 是否要避免直接借用其他语言术语

### 4.3 风险

如果不区分：

- 业务建模能力会变弱
- 语言的强类型优势会被削弱

如果区分方式过重：

- 语法学习成本会升高
- 语言可能引入过多既有语言概念

## 5. 课题三：受约束类型如何定义

### 5.1 背景

示例中已经出现了这种写法：

```yan
let email = check input.email as Email else CreateUserError.InvalidEmail
```

这里的 `Email` 看起来不是普通类型，而是“带约束的类型”。

### 5.2 需要回答的问题

- `Email` 是标准库内置类型，还是用户可定义类型
- 受约束类型的声明形式是什么
- 受约束类型和普通 `record`、基础类型之间是什么关系
- `check ... as Email` 背后是校验、转换，还是两者兼有

### 5.3 候选方向

可能的方向包括：

1. 标准库直接内置一批受约束类型
2. 语言允许用户声明受约束类型
3. 首版只支持标准库内置，用户自定义留到后续

### 5.4 当前意义

这个问题会直接决定 Yan 是否能自然表达：

- 邮箱
- URL
- UUID
- 手机号
- 各类领域值对象

## 6. 课题四：校验语法与类型提升如何结合

### 6.1 当前背景

目前候选写法是：

```yan
let email = check input.email as Email else CreateUserError.InvalidEmail
```

### 6.2 核心问题

这里不仅是“校验一个值”，还涉及：

- 是否产生一个新值
- 新值的类型是否从 `Str` 提升为 `Email`
- 校验失败如何进入错误控制流

### 6.3 需要定下的内容

- `check` 是否为关键字
- `as` 在这里表示转换、断言还是约束检查
- 失败路径是否统一使用 `else`
- 这种语法是否应成为受约束类型的标准入口

## 7. 课题五：泛型包装类型的地位

### 7.1 当前背景

当前文档中已经使用了：

- `Option<T>`
- `Result<T, E>`
- `Json<T>`

### 7.2 需要明确的问题

- 这些类型是否都属于语言官方推荐核心模型
- `Option<T>` 和 `Result<T, E>` 是否视为基础标准类型
- `Json<T>` 是标准库包装类型，还是 endpoint 参数语法的临时方案

### 7.3 课题意义

这关系到 Yan 的类型系统边界：

- 哪些能力属于语言核心抽象
- 哪些能力属于标准库
- 哪些只是暂时过渡语法

## 8. 课题六：是否需要“领域类型系统”这一层

### 8.1 问题描述

Yan 如果要强调后端开发体验，仅有基础类型和 `record` 可能不够。

还需要考虑是否要系统性支持：

- 标识类型，例如 `UserId`
- 受约束字符串类型，例如 `Email`
- 数据库映射类型
- 请求输入类型
- 响应输出类型

### 8.2 实际意义

如果这层能力设计得好，Yan 的类型系统就不只是“静态类型”，而是“对后端业务建模友好”。

如果这层能力缺失，Yan 可能只是把通用语言换了个壳。

## 9. 建议的讨论顺序

建议按以下顺序推进：

1. 先定 `UserId` 这类业务标识类型的定位
2. 再定“类型别名”和“新类型”是否同时存在
3. 再定 `Email` 这类受约束类型的定义方式
4. 再定 `check ... else ...` 是否作为标准校验入口
5. 最后统一 `Option`、`Result`、`Json` 等包装类型在语言中的层级

## 10. 当前结论

当前可以先记录的临时结论如下：

- `UserId` 应视为真正的类型，而不是普通字段名
- Yan 需要一种表达“独立业务类型”的机制
- Yan 很可能需要区分“类型别名”和“新类型”
- `Email` 这类受约束类型需要系统化设计，不能只靠示例零散出现
- 校验语法最终必须和类型提升、错误控制流统一起来
